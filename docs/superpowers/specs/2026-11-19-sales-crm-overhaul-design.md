# Отдел продаж: CRM по образцу AmoCRM — дизайн

Дата: 2026-11-19 · Статус: на утверждении

## 1. Зачем

Отдел продаж просит «максимальный аналог AmoCRM, чтобы не было каши на доске».
Конкретные запросы:

1. Заявки из WhatsApp сразу попадают в CRM, переписка ведётся из карточки лида.
2. Задачи и напоминания по лидам.
3. Когда лид переходит на «Встречу», встреча автоматически появляется в
   календаре встреч.
4. Адахан выбирается клоузером: сейчас на календаре нельзя отметить его встречи.

Сейчас продажи работают в двух несвязанных местах и вручную переносят данные
между ними. Цель — одно рабочее место, где у каждого лида видно этап, переписку
и следующий шаг.

## 2. Что есть сейчас (по коду, ветка `main` @ 58a40f7)

- **Две доски.** Воронка (`/leads`, `FunnelView`) построена на `LeadStage`, а
  переход на этап запускает действия (`services/leads.py::change_lead_stage`):
  «Встреча» создаёт `Meeting`, «Договор» — сделку и график оплат и т. д.
  Отдельная доска `/leads/board` (PR #3, миграция `021`) хранит свои столбцы в
  `lead_board_columns` / `lead_board_placements` и **намеренно не меняет этап**.
  Поэтому перенос карточки в столбец «Встреча» на этой доске ничего не создаёт.
  Зачем понадобилась отдельная доска, никто не знает.
- **Тип этапа угадывается по названию** (`_stage_kind`: «встреч» → meeting,
  «договор» → contract …), и фронтенд повторяет эту логику (`TransitionModal.stageKind`).
  Если этап переименовать, действия ломаются.
- **Клоузер определяется по тексту должности**: `_CLOSER_POSITIONS =
  {"Клоузер", "Финансовый директор"}` на бэкенде и две копии на фронтенде.
  Вдобавок календарь встреч берёт клоузеров только из участников отдела
  продаж (`SalesMeetingsCalendar.tsx:82`). У Адахана на проде, скорее всего,
  другая должность (в HANDOFF указано «Финансы») или он не состоит в отделе
  продаж. Поэтому его нет в списке.
- **Время встреч сдвинуто на 6 часов (вероятный баг).** `_handle_meeting_stage`
  собирает `meeting_date + meeting_time` и помечает результат как UTC, хотя
  пользователь вводит время по Бишкеку. Календарь (`MeetingModal`) переводит
  время в UTC правильно. В итоге встреча на 12:00, созданная через смену этапа,
  отображается в 18:00. Тестов на это нет. Перед исправлением подтвердить тестом.
- **Задачи.** У лида есть только `next_action_type` / `next_action_at`. У
  `Task` (личные доски) уже есть `lead_id`, `owner_id`, `completed_at`,
  `start_at`. Задачи видны в личном календаре (`routers/calendar.py`), а
  просроченные попадают в колокольчик (`routers/notifications.py`).
- **WhatsApp.** Интеграции нет. Для идемпотентности при приёме внешних лидов
  есть `Lead.external_lead_id`.
- **Обновление в реальном времени.** WebSocket и SSE нет, есть только опрос.
- **`/media/` отдаётся nginx публично, без авторизации.** Это важно для вложений
  из WhatsApp (§6.4).

## 3. Цели, не-цели, анти-цели

**Цели**
- Отдел продаж работает в Espada без параллельной таблицы и без WhatsApp на
  телефоне как основного инструмента.
- Каждое входящее сообщение WhatsApp с нового номера за несколько секунд
  становится лидом.
- Перенос лида на этап «Встреча» сразу создаёт встречу в календаре клоузера, с
  правильным временем.
- У каждого активного лида видно следующий шаг, а лиды без задачи и с
  просроченной задачей бросаются в глаза.
- Адахана (и любого другого сотрудника) можно назначить клоузером.

**Не-цели (сейчас)**
- Telegram, Instagram и другие каналы. Чат-боты и автоответы.
- Массовые рассылки.
- Несколько номеров WhatsApp (сейчас один общий номер отдела).
- Импорт переписки, которая была до подключения.
- Официальный WhatsApp Cloud API.
- Напоминания в Telegram. Позже, скорее всего, будет Telegram-бот, поэтому
  точку отправки закладываем заранее (§5.4).
- Мобильное приложение.

**Анти-цели (провал, даже если формально «работает»)**
- Входящая заявка теряется молча, например номер отключился и никто не узнал.
- Лиды дублируются: один клиент — две карточки.
- Номер заблокирован из-за поведения системы.
- Ломается существующая история: этапы, сделки, оплаты, встречи.
- Время встреч показывается неверно.
- Переписка с клиентами доступна по публичной ссылке.

## 4. Подходы

### 4.1 Подключение WhatsApp
| Вариант | Плюсы | Минусы |
|---|---|---|
| **Свой сервер: Evolution API (QR)** ✅ выбран | Без абонентской платы, переписка остаётся у нас, Docker рядом с Espada | Обновлять и обслуживать самим; неофициально — есть риск блокировки |
| Облачный посредник по QR (Wappi, Green API, Whapi) | Готовый сервис, поддержка | Платно; переписка идёт через чужой сервер; документацию Wappi не нашли |
| Официальный Cloud API (Meta) | Нет риска блокировки | Верификация бизнеса, отдельный номер только под API, платные шаблоны и окно 24 часа |

Выбран вариант по QR, на своём сервере. Посредник спрятан за адаптером
(§6.2), чтобы его можно было заменить без переделки CRM.

### 4.2 Доска
| Вариант | Итог |
|---|---|
| **Столбцы = этапы воронки, как в AmoCRM** ✅ | Одна доска, перенос запускает действия этапа |
| Оставить свободные столбцы и привязывать к ним этапы | Две сущности для одного и того же, путаница остаётся |
| Оставить как есть и чинить только календарь | Не решает «кашу» |

### 4.3 Задачи по лидам
| Вариант | Итог |
|---|---|
| **Переиспользовать `Task` с `lead_id`** ✅ (моё решение) | Задача сразу видна на личной доске и в календаре сотрудника, а уведомления о просрочке уже работают |
| Новая таблица `lead_tasks` | Чище по смыслу, но придётся заново делать календарь, уведомления и личные доски |

## 5. Дизайн по частям

Порядок выкладки: **1 → 2 → 3 → 4**. Каждая часть выкладывается отдельно
(сначала `dev`, затем `main`) и полезна сама по себе. Миграции начинаются с `022`.

### 5.1 Часть 1 — Клоузер как признак сотрудника

- `users.is_closer: bool` (по умолчанию `false`). Миграция включает признак
  тем, у кого `position IN ('Клоузер', 'Финансовый директор')`, и
  пользователю с email `adahan@…`.
- В карточке сотрудника (`UserModal`, `/admin/staff`) появляется галочка
  «Клоузер», её меняет admin.
- Бэкенд: `_CLOSER_POSITIONS` заменяется на `user.is_closer`. Поле
  возвращается в `UserOut`.
- Фронтенд: одна функция `isCloser(user)`, которая читает `is_closer`. Копии в
  `SalesDepartmentView` и `SalesMeetingsCalendar` удаляются. Списки клоузеров
  строятся по **всем активным пользователям с `is_closer`**, без требования
  состоять в отделе продаж. Во всех выпадающих списках «Клоузер»
  (`TransitionModal`, `CreateLeadModal`, `MeetingModal`, карточка лида) показываются
  только клоузеры, а не все сотрудники.
- Права на смену статуса встречи не меняются: клоузер этой встречи или admin.

### 5.2 Часть 2 — Одна доска по этапам

**Тип этапа хранится явно.**
- `lead_stages.kind` — одно из `generic | meeting | contract | waiting_payment | won | lost`.
  Миграция заполняет поле по текущей логике `_stage_kind`. После этого
  `_stage_kind` и `stageKind` на фронтенде читают поле, а не название.
- В «Справочники → Этапы воронки» (`StagesSection`) добавляется выбор типа.
  Этапы по-прежнему можно добавлять, переименовывать, перекрашивать и
  переставлять, а архивировать вместо удаления, как сейчас.

**Доска `/leads/board`.**
- Столбцы — активные этапы в порядке `position`. Лиды — активные (`status=active`).
- **Закрытые лиды (этапы `won` / `lost`) на доске не показываются** (моё
  решение, как в AmoCRM). Внизу доски две зоны для переноса: «Оплачено» и
  «Минус». Закрытые лиды видны по фильтру «Показать закрытые» и в списке
  `/leads`. Сейчас переход в won/lost не меняет `Lead.status`, и это остаётся
  так: «открытый лид» = `status=active` и этап не типа `won`/`lost`.
- **Повторный вход в «Встречу».** Если у лида уже есть встреча со статусом
  `scheduled`, форма перехода открывает **её** для переноса, а не создаёт новую
  (моё решение: иначе Встреча → Созвон → Встреча плодит дубли в календаре).
  Уход с этапа встречу не трогает: её статус ставит клоузер, как сейчас.
- Перенос карточки:
  - этап типа `generic` — этап меняется сразу (`PATCH /api/leads/{id}/stage`);
  - остальные типы — открывается существующий `TransitionModal`. Если нажать
    «Отмена» или сервер вернул ошибку (например, неполная оплата), карточка
    возвращается в исходный столбец, а пользователь видит текст ошибки;
  - «Встреча» — дата, время, длительность, клоузер, адрес и комментарий. Встреча
    сразу появляется в календаре встреч отдела и в календаре клоузера.
- Ручной порядок внутри столбца **не храним** (моё решение). Сортировка по
  важности: непрочитанные сообщения WhatsApp → просроченная задача → нет
  задачи → по дате последней активности.
- Карточка показывает имя и компанию, услугу, сумму сделки (если есть), сеттера
  или клоузера, ближайшую задачу (красная — если просрочена, «Нет задачи» —
  если её нет) и счётчик непрочитанных WhatsApp.
- Фильтры: существующие (`LeadFiltersBar`) плюс быстрые «Мои лиды» (я сеттер или
  клоузер), «Без задачи», «Просрочено», «Неразобранные» (нет сеттера).
- Доска обновляется опросом раз в 30 секунд, пока вкладка активна.
- Канбан в `FunnelView` убирается: `/leads` остаётся списком со статистикой, а
  доска — единственный канбан. Кнопки действий с карточек воронки
  (`ActionDropdown`) переносятся в меню карточки на доске.

**Старые свободные столбцы.**
- Перед выкладкой выгрузить с прода `lead_board_columns` и распределение лидов
  по ним. Вместе с руководителем продаж каждый столбец либо сопоставить с
  этапом, либо добавить этапом.
- Миграция удаления сначала сохраняет обе таблицы в JSON-бэкап (или выкладка
  требует `pg_dump` этих таблиц), затем удаляет их вместе с эндпоинтами
  `/api/lead-board/columns*`. Этапы лидов, история, встречи и финансы не трогаются.

**Исправление времени встречи.** `_handle_meeting_stage` считает
`meeting_date + meeting_time` временем по Asia/Bishkek и переводит в UTC.
Сначала пишется тест, который воспроизводит сдвиг. Существующие встречи,
созданные через смену этапа, могут быть сдвинуты на 6 часов: проверить на копии
прода и, если так и есть, исправить отдельной миграцией данных (отбор по
`meetings.lead_id IS NOT NULL` и записи в `lead_stage_history` в тот же момент).
Строитель решает только после проверки, массово ничего не исправлять вслепую.

### 5.3 Часть 3 — Задачи и напоминания по лидам

**Модель.** Задача по лиду — это `Task` с `lead_id`. Добавляются:
- `tasks.due_at: datetime | null` — точное время (UTC). `due_date` заполняется
  из `due_at` (дата по Бишкеку), чтобы существующие экраны и уведомления
  работали без изменений;
- тип задачи — в существующем `task_type`: «Позвонить», «Написать»,
  «Встреча», «Другое»;
- `tasks.result: text` — итог, который вводится при завершении.

Задача кладётся на личную доску ответственного, в первый столбец без `is_done`.
Если доски нет, она создаётся так же, как сейчас.

**Права на задачи по лидам** (мои решения):
- Ответственным можно назначить любого участника отдела продаж или клоузера.
  Например, сеттер может поставить задачу клоузеру. Это исключение из правила
  `tasks.py`, по которому задачу ставят только на свою доску, и действует оно
  только для задач с `lead_id`, создаваемых через API лида.
- Редактировать и завершать задачу могут ответственный, автор, admin и
  `is_founder`.
- Задачи с `lead_id` **не показываются** на публичных ссылках досок
  (`BoardShare`, миграция 019): там имена клиентов.

**Карточка лида.** Блок «Задачи»: создать (тип, когда, ответственный — по
умолчанию я, текст), завершить с итогом. Создание и завершение пишутся в ленту
активности лида (`LeadActivity`).

**Подсказки по образцу AmoCRM** (мои решения):
- После переноса на любой этап, кроме `won` и `lost`, предлагается поставить
  следующую задачу. Это не обязательно.
- Переход в `won` или `lost` закрывает открытые задачи лида с итогом «Лид закрыт».

**Старое поле «следующее действие».** У активных лидов с `next_action_at` из
`next_action_type` / `next_action_at` создаётся задача: ответственный — сеттер,
а если его нет — клоузер. После этого поля не показываются в интерфейсе (как
`potential_amount`) и не редактируются.

**Напоминания.**
- В колокольчике (`routers/notifications.py`) появляются «Через 15 минут:
  <задача>» и «Просрочено: <задача>» со ссылкой на лида.
- Все напоминания проходят через одну функцию, например
  `services/reminders.py::due_reminders(user)`. Позже Telegram-бот будет
  отправлять то же самое, не переписывая логику.

### 5.4 Часть 4 — WhatsApp

**Инфраструктура.**
- Сервис `evolution` (Evolution API v2, версию закрепить) в `docker-compose.yml`.
  Он работает только во внутренней сети, без `ports` и без проксирования в
  nginx. Хранилище — отдельная база `evolution` в существующем Postgres и том
  для сессии, чтобы после перезапуска QR не сканировать заново.
- Новые переменные `.env`: `EVOLUTION_API_KEY`, `WHATSAPP_WEBHOOK_SECRET`,
  `WHATSAPP_INSTANCE` (имя инстанса).
- Не забыть `docker-compose.tunnel.yml` (прод на OMV через Cloudflare Tunnel) и
  обновить `DEPLOY.md`.

**Адаптер.** `backend/app/services/whatsapp/`:
```
provider.py   — интерфейс: create_instance(), get_qr(), status(), logout(),
                send_text(jid, text), send_media(jid, file, caption),
                parse_webhook(payload) -> list[InboundEvent]
evolution.py  — реализация для Evolution API
inbound.py    — обработка событий: поиск или создание лида, сохранение сообщения
```

**Вебхук.** Evolution отправляет события на
`http://backend:8000/api/whatsapp/webhook/{WHATSAPP_WEBHOOK_SECRET}` по внутренней
сети. В nginx путь `/api/whatsapp/webhook/` закрыт (`deny all`). Обрабатываются
события: новое сообщение, статус доставки, состояние подключения. Обработчик
идемпотентен: сообщение с тем же `external_id` повторно не сохраняется.

**Данные.**
- `whatsapp_chats`: `id`, `remote_jid` (unique), `phone` (нормализованный),
  `lead_id` (FK, `SET NULL`; текущий лид), `push_name`, `last_message_at`,
  `unread_count`, `is_ignored`.
- `whatsapp_messages`: `id`, `chat_id`, `external_id` (unique), `direction` (in/out),
  `sender_user_id` (кто из сотрудников отправил; `null` — с телефона или от
  клиента), `type` (text/image/document/audio/video/other), `body`, `media_path`,
  `media_mime`, `status` (pending/sent/delivered/read/failed), `sent_at`.

**Входящее сообщение с нового номера.**
1. Нормализуем номер (только цифры; местный `0XXXXXXXXX` → `996XXXXXXXXX`) и ищем
   лида по нормализованным `phone` / `whatsapp`. Для поиска понадобится
   нормализованная колонка с индексом; как сделать — решает строитель.
2. Чат привязывается к лиду так (мои решения):
   - есть **открытый** лид (`status=active`, этап не `won`/`lost`) — к нему;
   - есть только лид в `won` (действующий клиент) — к нему, а сеттер и
     клоузер видят в колокольчике «Клиент написал»: это поддержка или допродажа,
     не новая сделка;
   - есть только лид в `lost` или архивный — создаётся новый лид, в комментарии
     ссылка на старый.
3. Если не нашли — создаём лид: этап «Новый лид» (первый активный этап типа
   `generic`), источник «WhatsApp», имя из профиля WhatsApp или номер,
   `whatsapp = phone`, **без сеттера**.
4. В колокольчике у отдела продаж — живая строка «N неразобранных заявок из
   WhatsApp», которая считается при запросе, как остальные уведомления.
   Отдельная таблица уведомлений с отметкой «прочитано» не делается, она
   понадобится вместе с Telegram-ботом.

**Чат принадлежит номеру, а не лиду** (моё решение). `whatsapp_chats` — один
на номер, `lead_id` — текущий лид. Любой лид с этим номером показывает всю
историю переписки с ним. Когда у клиента появляется новый лид, чат просто
переключается на него, а у старого лида переписка остаётся видна.

**Не каждый номер — лид.** На общий номер пишут поставщики, сотрудники, спам.
- Кнопка **«Не лид»** в чате и на карточке «Неразобранного» помечает чат
  `is_ignored`, архивирует созданный лид, и новые сообщения с этого номера лиды
  не создают. Чат остаётся в разделе «Прочие чаты», откуда пометку можно снять.
- Если сотрудник **сам написал с телефона** на неизвестный номер, создаётся
  только чат без лида. Из него можно сделать лида вручную.

**Распределение.** Один номер, правил распределения пока нет. Новый лид
попадает в «Неразобранные» (фильтр и счётчик на доске). Кнопка «Взять себе»
назначает текущего пользователя сеттером. Если сеттера нет, а сотрудник
ответил из Espada, он становится сеттером автоматически.

**Чат в карточке лида.**
- Вкладка «WhatsApp»: история, отправка текста, фото и файлов, у каждого
  исходящего — кто отправил и статус (отправлено / доставлено / прочитано /
  ошибка). Сообщения, отправленные с самого телефона, тоже видны с пометкой
  «с телефона».
- Открытая вкладка опрашивает новые сообщения каждые 5 секунд. Открытие
  чата обнуляет `unread_count`.
- Если клиент ещё не писал, ему можно написать первым, но только по одному
  лиду. Массовой отправки нет.
- Голосовые и видео: сохраняем и даём скачать или прослушать. Отправка голосовых
  — не цель.

**Вложения и доступ.** Файлы клиентов **не кладутся** в публичный `/media/`.
Они хранятся в `MEDIA_ROOT/whatsapp/` (вне alias nginx) и отдаются эндпоинтом
`GET /api/whatsapp/media/{message_id}` с проверкой прав. Фронтенд получает их
через `fetch` с токеном и показывает через blob URL.

**Права.** Читать и отправлять могут admin, `is_founder`, участники отдела
продаж (членство в `Department` со `slug="sales"`, а не должность) и
пользователи с `is_closer`. Тот же круг получает уведомления о заявках:
`_is_sales` в `notifications.py` переводится на это же определение. Остальные видят лида как сейчас, но
вкладки WhatsApp у них нет.

**Подключение номера — `/admin/whatsapp`** (только admin): статус, QR для
подключения (обновляется), «Переподключить», «Отключить». Если номер
отключился, все админы видят в колокольчике красное «WhatsApp отключён —
заявки не принимаются». Отключение определяется по событию
подключения, а для надёжности ещё и периодической проверкой статуса.

**Что игнорируем:** групповые чаты, статусы (stories), служебные события.

## 6. Риски

- **Блокировка номера.** Неофициальное подключение всегда несёт риск. Чтобы его
  снизить: никаких рассылок, «написать первым» только по одному лиду. Отделу
  продаж стоит объяснить, что номер может быть заблокирован и что нужен
  запасной план (новый номер, переподключение).
- **Обновления WhatsApp ломают Evolution API.** Версию закрепляем; обновляем
  осознанно, сначала на `dev`.
- **Удаление старых столбцов** — данные PR #3 теряются. Нужен бэкап и
  согласование с руководителем продаж (§5.2).

## 7. Что оставлено строителю

- Конкретная версия образа Evolution API и его настройки.
- Вёрстка доски, карточки и чата — в стиле текущего интерфейса (`components/ui`).
- Способ хранения нормализованного телефона (колонка или функциональный индекс).
- Интервалы опроса (предложены 30 с для доски и 5 с для чата) — можно менять.
- Обновление MCP-инструментов (`mcp-server/server.py`) под новые поля — по
  ходу, если существующие инструменты лидов перестанут соответствовать API.
- Обновить `README.md`, `docs/product-spec.md`, `DEPLOY.md` по каждой части.

## 8. Ветки и выкладка

Разработка — в `dev` (фичевые ветки от `dev`), прод — `main`. Каждая часть
проходит тесты бэкенда и фронтенда, а миграции проверяются upgrade/downgrade
на PostgreSQL 16, как в предыдущих PR.

**Проверка до прода.** Отдельного тестового сервера нет. Части 1–3 проверяются
локально на копии продовой базы. Часть 4 проверяется **локально с отдельным
тестовым номером WhatsApp** (решение команды). Номер отдела продаж к локальной
среде **никогда не подключается**, иначе заявки разойдутся по двум базам. Для
этого нужен `docker-compose` для локальной разработки с сервисом `evolution`
(или профиль compose). Номер отдела подключается только на проде, после
проверки на тестовом номере.
